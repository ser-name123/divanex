Addendum Audit of the same date

Correction to the previous audit

Blog CMS Studio was marked Working. It was not working at all. That classification was made by reading the screen, which offers create, edit, publish and delete. Nobody checked whether any of it reached the database. It did not.

The blog_posts table had never been created — nothing in scripts/setup-db.js made it. Reads fell through to the seed file, writes went to a module-level array that lives inside one serverless instance and is gone by the next request, and the database error was discarded rather than checked, so the route reported success. Publishing an article said it worked and lost it.

It went unnoticed because the console's blog screen never asked the server either — it rendered the same seed. The ten posts on screen always matched the ten on the site, and a new article stayed in the list right up until the page was reloaded.

Fixed and verified: the table exists with RLS forced, holds the ten live articles, failed writes now throw rather than being swallowed, and the console reads from the database.

The lesson applies to the rest of this document. Every status below was taken from running the code or driving the live site, not from the presence of a button. Where that distinction mattered it is stated in the evidence column.

Part 3

Defects found that the specification does not list

Found while checking its items. Two were already losing data; two more would have gone wrong the first time a feature was used. All four are fixed or small.

DefectStateDetail
Blog saved nowhereFIXED Table never created; writes went to per-instance memory and the error was discarded. Publishing reported success and lost the article.
Drafts were publicFIXED /api/blog?status=draft honoured the parameter with no authentication, so every unfinished article would have been readable by anyone. Nothing leaked only because no draft existed yet. Now 401 for an anonymous caller; verified live.
Analytics never reportedFIXED The Google tag was in the markup and refused by the site's own Content-Security-Policy on every page load. The property had received nothing at all.
39 links to pages nobody wroteFIXED Portfolio cards linked to case studies that did not exist.
Sitemap ignores noindexOPEN Draft posts are excluded but the per-page flag is never read. Nothing is wrong today because no page is set to noindex; it breaks the first time the setting is used. An hour's work.
Blog changes leave no audit recordOPEN Posts, sprints and subscriber deletions are never recorded. The action names are declared in the audit type and nothing writes them. Half a day.
Rate limiting is per-instanceOPEN 200 requests a minute counted in the memory of whichever serverless instance answers, so the real limit is neither 200 nor knowable. It can also catch several genuine visitors behind one office network. A security control, so it needs a decision rather than a quiet change.
Two unused componentsOPEN EngagementModels.tsx and SecurityComplianceSection.tsx are complete and rendered nowhere.

On the ordering. The specification puts the audit first, which is done, then page manager and media together. Two changes are worth considering: the Part 3 defects come before anything new, because two of them are live faults; and SEO warnings move ahead of the media library, because they cost three days and stop mistakes reaching the website.

Acceptance criteria today

Of the twenty in §11, five can be demonstrated now: the audit report exists with evidence; published content appears on the correct live URL; new services and blog posts get their own public pages; drafts and protected operations are refused to unauthorised users; and the existing forms, newsletter, chat, analytics, navigation and notifications all work. The sitemap and robots criteria pass except for the noindex rule. The remaining fourteen depend on the phases above.
