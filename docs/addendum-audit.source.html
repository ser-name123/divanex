How this was checked

Every status below came from reading the code or driving the running site, not from the handbook. Where a claim could be tested against the live site it was, and three findings in this report contradict what the handbook says — those are corrected in Part 4.

WORKING built and verified   PARTIAL exists but short of the requirement   MISSING no implementation   N/A does not apply here
Headline: the addendum is right about the big items, and wrong about one. Six of the seven "not built yet" features are genuinely absent. Revision rollback is the exception — a working whole-content backup and restore already exists; what is missing is per-record version history.

The audit also surfaced four defects the addendum does not mention, found while checking the items it does. They are in Part 3 and matter more than some of the P2 work.

Part 3

Defects the addendum does not list

Found while checking the items above. Each is small to fix and two of them are losing information today.

1. Blog posts leave no audit record

Posts live in their own table rather than the content store, and that path never calls the audit recorder (blogStore.ts, api/blog/route.ts). Anyone with content rights can publish, rewrite or delete an article and the trail will not show it. The same is true of client sprints and subscriber deletions.

The action names project.created, subscriber.deleted and chat.deleted are declared in the audit type and never written by anything — the intent was there and the calls were never added.

Action: record the same diffs the content store records. Half a day, and it closes a real hole in section 3.4.

2. The sitemap ignores the noindex flag

Draft posts are correctly excluded, but the per-page noindex setting is never read when the sitemap is built (sitemapEntries.ts). Setting a page to noindex in the console would leave it listed in the sitemap — telling search engines to crawl a page that then asks not to be indexed.

No page is currently set to noindex, so nothing is wrong on the live site today. It will go wrong the first time the feature is used, which is the worst way to find out.

Action: filter on the flag. An hour.

3. Rate limiting is per-instance and in memory

The limit is 200 page requests per minute per address, counted in the memory of whichever serverless instance answers (proxy.ts:153). On a platform that runs many instances the real limit is neither 200 nor predictable, which makes it weaker protection than it looks. It can also catch several genuine visitors sharing one office or mobile network.

Action: move the counter to the database so one limit is actually enforced, and reconsider the number. This is a security control, so it should be a deliberate decision rather than a quiet change.

4. Two components are built and never rendered

EngagementModels.tsx and SecurityComplianceSection.tsx are complete and unreferenced. They ship in the repository and confuse anyone searching for where something is rendered.

Action: delete them, or wire them in if they were meant to be live.

Part 4

Corrections to the handbook

The addendum was written from the handbook, so where the handbook was wrong the addendum inherits it. Three corrections, and the handbook itself will be reissued.

Handbook saysActually
"There is no rollback." A full content backup and restore exists and works — export to a file, import it back with a confirmation. What is missing is per-record version history, which is a narrower gap and a smaller job.
"Nothing flags a broken link." Backup, Audit & Search does find links pointing at pages that no longer exist. The missing checks are the SEO ones: duplicate addresses, over-long descriptions, missing image descriptions.
Audit trail covers content changes. True for everything except blog posts, client sprints and subscriber deletions. See Part 3.

Suggested order, and why it differs from the addendum

The addendum puts draft, media and restore first. Two changes are worth considering.

OrderWorkReason
1The four defects in Part 3 Not in the addendum, all small, and two are losing information or will mislead search engines the first time a feature is used.
2SEO validation warnings P1 in the addendum, the cheapest item on the list, and it prevents mistakes rather than recording them.
3Draft, preview and publish The largest safety gain. Everything published today goes live on the first keystroke after Save.
4Section add, duplicate, reorder, hide Understated in the addendum. Without it a page's shape still needs a developer, which is most of what a CMS is for.
5Media library Needs a storage bucket and an upload path; worth doing properly once rather than quickly twice.
6Per-record restore, redirects Redirects matter more once addresses start changing, which the draft and section work will cause.
7Scheduled publishing, location pages Location pages are blocked on real market content, not on code.
